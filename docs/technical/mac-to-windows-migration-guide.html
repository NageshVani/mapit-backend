Mac → Windows Migration Guide

MapIt-Backend development environment · written 2026-09-27 · use when the new Windows PC arrives

Core principle: don't copy the project folder across machines. Recreate the environment from the sources of truth — the GitHub repo and your own secrets in Vercel/your password manager — rather than dragging over macOS-specific files (.DS_Store, absolute paths, a node_modules folder compiled for the wrong OS) that can silently break on Windows.

1. Install prerequisites on the Windows PC

1Git for Windows (includes Git Bash) — git-scm.com/download/win

2Node.js — match the version this Mac is on. Check it here first:

node -v

Install the same major version on Windows (nvm-windows if you want to manage multiple versions later).

3VS Code (or your editor) + the Claude Code extension/CLI.

4GitHub CLI (gh) — same tool you already use for PRs.

2. Re-establish GitHub authentication

Don't copy SSH keys or tokens across machines — generate fresh ones on the new PC instead.

gh auth login

If you also use raw git over SSH, generate a new key pair on Windows (ssh-keygen) and add the public key to your GitHub account under Settings → SSH and GPG keys.

3. Clone the repo fresh

git clone https://github.com/NageshVani/mapit-backend.git
cd mapit-backend
git checkout uat

This brings over the full commit history plus everything already tracked in git — including CLAUDE.md and CONTEXT.md, so Claude Code on the new machine has full project context immediately.

4. Install dependencies

npm install
Never copy the node_modules folder itself from the Mac — any native/compiled modules are built per-operating-system and will fail silently or loudly on Windows. Always reinstall from package.json.

5. Recreate .env — the one step that needs care

.env is git-ignored on purpose (Rule 8 of CLAUDE.md) and was never committed, so the clone above will not bring it over. You have to rebuild it by hand:

1Copy .env.example to .env on the new machine — it has every variable name, just no values.

2Fill in each real value. The fastest legitimate source is the Vercel dashboard → your project → Settings → Environment Variables (Production/Preview) — every key MapIt uses in production is already sitting there, so you're copying, not memorizing.

3Anything not in Vercel (e.g. a purely-local dev value) — pull from your password manager.

Do not transfer the raw .env file itself across machines by email, AirDrop, USB drive, or chat — that moves an unencrypted secrets file (including SUPABASE_SERVICE_ROLE_KEY) outside your control. Re-typing/copy-pasting each value from Vercel's dashboard into a fresh file on the new machine is the safe path.

6. Re-authenticate the CLIs you use

Vercel CLI

npm i -g vercel
vercel login

Supabase CLI (if you use it locally for migrations/scripts)

npm i -g supabase
supabase login

7. Sanity-check the environment

npm run dev

Confirm:

✓the server boots on the expected port (default 3001)

✓GET /api/config returns the expected public keys (Supabase anon key, Mapbox token)

✓the frontend loads at localhost:3001 and the map renders

✓you can sign in with a test account (confirms Supabase Auth + .env values are correct)

8. Retire the Mac's copy of the secrets

Once the Windows setup is confirmed working, if the Mac is being repurposed, sold, or handed off — delete its local .env file, and rotate any key you're not fully sure about (Supabase service-role key, Mapbox token). Don't leave production secrets sitting on a machine you no longer control.

What does not need special handling

Everything actually durable about the project — code, migrations, CLAUDE.md, CONTEXT.md, every doc in docs/ — already lives in the GitHub repo and comes over free with git clone. The "migration" is really just: re-authenticate, re-type secrets, reinstall dependencies. Nothing about the project's structure needs to change to make this move possible.
