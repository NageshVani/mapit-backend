Database Backup & Restore Runbook

Production Supabase project jneoxwumccmjwaojfazh (org "MapIt Production", Pro plan, Singapore). First drill: 2026-10-15 — PASSED. Written by James for Nagesh & Arun.
The one rule: under Database → Backups → Scheduled backups, the plain "Restore" button overwrites the live production database and takes the site offline while it runs. Everything written since that backup is lost. Never click it for a test, and never in an emergency without a written plan agreed by Nagesh + Arun.

1. What we have

  • Daily physical backups, kept 7 days, taken about 21:04 UTC (01:04 UAE / 02:34 IST next day). Times in the dashboard are UTC (+0000).
  • No Point-in-Time Recovery (paid add-on, not bought). Worst case we lose up to ~24 h of changes.
  • Not in the backup: Storage files (listing photos), Auth settings, API keys, Edge Functions. The UAT project (Free plan) has no backups.

3. Drill procedure (repeat ~1 month after launch, then every 3 months)

  1. Production project → Database → Backups → "Restore to new project" tab → newest backup → Restore.
  2. Confirm dialog must say "create a new project and restore your database to it". Name mapit-restore-test; generated password (don't keep it). Cost shown is monthly (~$9.68 Micro) but billed by the hour (~$0.013/h).
  3. Wait until the new project shows Healthy (~10–20 min).
  4. SQL Editor (check the project picker every time), on production and the copy, save each single result cell outside the repo in C:\dev\mapit\:
    • database/scripts/session-9-restore-test-counts.sql → counts-prod.json / counts-restore.json (row counts only, no PII)
    • database/scripts/session-9k-schema-inventory.sql → schema-prod-YYYY-MM-DD.json / schema-restore.json
  5. Compare: counts must match (differences only from activity after the backup — see newest_audit_log); then node database/scripts/compare-schema-inventory.js <prod.json> <restore.json> → "Schemas match". Expected difference: the copy runs a newer Postgres minor version.
  6. Delete the copy the same day (it holds real user data): open it, check the address is not jneox…, Project Settings → General → Delete project → type the name. Then npm run smoke:prod.
  7. Record the result in section 6 and CONTEXT.md.
Gotcha: every Supabase project shows a "main · PRODUCTION" branch label in its header — that's the project's own default database branch, not MapIt production. Identify a project by its name and ref (jneox… = production).

4. Real emergency

4A. Preferred: restore to a new project, then switch over

Use when data is damaged (bad migration, wrong DELETE/UPDATE). Production stays up (read-only maintenance message if needed) while the copy is built and checked. If only a few rows/tables were lost, copy just those back from the new project into production instead of switching.

Switch-over checklist (the restored project has a new URL and new keys):

  1. Vercel → Production env: SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY → new project; redeploy production.
  2. Auth settings by hand: Site URL https://www.mapit.co.in, redirect URLs (mapit.co.in/**, www.mapit.co.in/**), "Confirm email" OFF, Email OTP length 6, Resend SMTP (smtp.resend.com:465, user resend), email templates, Google provider.
  3. Google Cloud Console → OAuth client → add the new https://<new-ref>.supabase.co/auth/v1/callback redirect URI.
  4. Storage: create bucket listing-photos (public) and copy the photo files over from the old project if it is still reachable; otherwise sellers re-upload.
  5. Re-run the schema inventory on the new project and compare with the last good prod file; npm run smoke:prod; one manual login + listing view.
  6. Keep the old project (paused) until everything is confirmed, then delete it.

4B. Last resort: in-place Restore

Only if production itself is unusable and a switch-over is not possible. Agree in writing (Nagesh + Arun) which backup and what is lost, put the site in maintenance first, then Backups → Scheduled backups → Restore. Afterwards: smoke test, manual checks, CONTEXT.md entry.
