Background Setup Modifications on Public Release

Beyond the already-planned upgrades — what else needs to change before and after the public launch button is pressed.

The sessions plan already covers: Vercel Pro upgrade, Supabase Pro upgrade, email verification step, Google OAuth redirect URLs, and OTP rate limit tuning. The items below are in addition to those.

Modification Why it is needed When Priority
Remove localhost from CORS allowlist Currently allows localhost:3000, localhost:3001, localhost:5500, 127.0.0.1:5500. These are dev-only origins and should not be reachable from production Express. An attacker running a local server could exploit the open CORS. Before go-live Critical
Re-enable Helmet CSP with an explicit allowlist Helmet's Content Security Policy is currently disabled globally (contentSecurityPolicy: false) to allow inline scripts and CDN resources. For a public marketplace, a proper CSP prevents XSS. The fix is to write an explicit policy that allows Leaflet CDN, Font Awesome, Google Fonts, and inline scripts specifically rather than disabling it entirely. Pre-launch hardening High
Nominatim usage policy compliance MapIt uses OSM Nominatim (free, no key) for reverse geocoding and address lookup. The OSM usage policy prohibits heavy commercial use from the shared tile server. Public traffic could hit their rate limits and your app silently stops showing addresses. Either self-host Nominatim on a $5/mo VM or switch to Geoapify free tier (2,500 req/day free, paid after that). Pre-launch Critical
Supabase Storage CDN configuration Listing photos are served directly from Supabase Storage URLs. Supabase Pro includes a CDN layer — it must be explicitly enabled in the dashboard. Without it, every photo request hits the origin, which is slow for Indian mobile users and can hit Supabase egress limits quickly. At Supabase Pro upgrade High
Orphaned photo cleanup job When a listing is deleted or expires, the photos in Supabase Storage are not automatically removed. After a few months of public use, Storage can fill with orphaned files. A cron job (or Vercel Edge Function on a schedule) should periodically delete storage objects with no matching listing row. Within 30 days of launch High
Supabase Row Level Security (RLS) full audit Every table — listings, profiles, messages, user_pins, invite_codes — needs RLS policies verified before public launch. A misconfigured policy could expose all listings, all user profiles, or all messages to unauthenticated queries. The spatial_ref_sys table is intentionally unrestricted (PostGIS system table) and is fine. Before go-live Critical
Error monitoring (Sentry or Vercel observability) Currently there is no error tracking. In production, silent failures (API 500s, edge function crashes, unexpected DB query results) go completely undetected until a user reports them. Sentry's free tier (5,000 errors/month) or Vercel's built-in observability dashboard covers this at zero cost for MVP scale. Day of launch High
Legal pages: Privacy Policy + Terms of Service The current ToS is a checkbox with no linked document. For a public marketplace in India, a published Privacy Policy is legally required under the IT Act (SPDI Rules) and is needed for Google OAuth consent screen approval. Without it, Google may disable the OAuth button for new users. Before go-live Critical
Resend email plan upgrade Resend free tier is 100 emails/day. With OTP sign-ins, listing expiry notifications, and "I'm Interested" emails at public scale, 100/day is exhausted by ~50 active daily users. Resend Starter is $20/mo for 50,000 emails/month. At launch or just before High
Supabase Auth email template branding Currently, OTP emails use Supabase's default unbranded template. Public users receiving "Supabase Auth" emails lose trust in the MapIt brand. Templates should be updated in Supabase → Auth → Email Templates to show the MapIt name, logo emoji, and consistent colours. Pre-launch Medium
Listing expiry notification emails Listings expire after 30 days (set in Session 3). Sellers have no visibility that their listing is about to expire. A cron or database trigger should send a Resend email 3 days before expiry: "Your MapIt listing 'title' expires in 3 days. Post it again to stay listed." Prevents ghost listings and keeps sellers engaged. Within first month Medium
Twilio India phone number setup SMS OTP (Twilio) is already wired. However, Twilio's India long-code SMS delivery has been unreliable post-2021 DLT registration requirement. You need to register a DLT-compliant header/entity on the TRAI portal (one-time, free) and link it to Twilio before OTP SMS works reliably for Indian phone numbers. Pre-launch if SMS OTP enabled High
PostGIS GiST index verification The listings query currently uses a JS haversine filter on all rows (no DB spatial index). This is fine at <1,000 listings but degrades linearly after that. Before public launch, confirm a GiST index exists on the (lat, lng) columns and run EXPLAIN ANALYZE on a representative query to ensure "Index Scan" (not "Seq Scan"). Pre-launch High
Supabase connection pooler (PgBouncer) Vercel serverless functions each open their own DB connection. At 50+ concurrent users, connection count exceeds Supabase Free limits (20 direct connections). Supabase's built-in PgBouncer pooler (Session Mode) should be enabled — it's a one-line connection string change in the backend config. Before >50 concurrent users Medium
robots.txt + sitemap.xml for SEO MapIt serves a single-page app. With no sitemap, Google's crawler sees nothing useful. A static /sitemap.xml listing the root domain + a minimal robots.txt (allowing all, blocking nothing) helps with organic discovery for "buy sell Bangalore" type searches. Within first month Medium
Open Graph / meta tags for link sharing When a listing URL is shared on WhatsApp or Twitter, the preview currently shows nothing meaningful. Adding <meta property="og:title">, og:description, and og:image tags (even if static for the landing) dramatically improves click-through on shared links — important for a marketplace that relies on WhatsApp sharing in India. Pre-launch Medium
Performance audit on slow mobile / 4G The frontend is a ~3,000+ line single HTML file that includes all CSS, all JS, and loads Leaflet (~150KB), Font Awesome, and Google Fonts from CDN. On a 4G Indian mobile connection, first paint can exceed 4 seconds. A rel="preload" directive for Leaflet and font-display:swap on Google Fonts reduces perceived load without a full rewrite. Pre-launch Medium
⚠️
Non-negotiable before public launch: Email verification (step-verify-email) must be implemented. Currently email_confirm: true in the admin API skips all email verification — anyone can register with someone else's email address. This is noted in CONTEXT.md as a known pre-public-launch gap and cannot ship to public users.

Types of Feedback to Expect from Public Users

Mapped to the actual features and known constraints of MapIt — not generic marketplace theory.

📍 Very Common

Location pin is wrong / GPS not accurate

The most common complaint in any map-based app. Cheap Android phones in India often have GPS drift of 50–200 m. Users will say "the pin shows my listing in the wrong place" or "I tapped on the map but it moved." The reverse-geocoding via Nominatim also occasionally returns a wrong locality name for pins near area boundaries.

🔑 Very Common

Login / OTP not received

OTP email not arriving (Resend → spam folder, or Resend daily limit hit), Google OAuth redirecting to the wrong page, or "Invalid or expired invite code" type errors even after invite codes are removed. Users rarely read error messages — they will report "login doesn't work" with no further detail.

🗺️ Common

Map doesn't load / shows blank tile

OpenStreetMap tile server throttles IPs that hit the free tile server without a custom User-Agent header set. At scale, tiles stop loading for some users. Also, older Android WebView versions have rendering issues with Leaflet. This appears as a blank grey map with no tiles.

📸 Common

Photo upload failing / taking too long

The 5-photo limit is enforced but the error message when it is exceeded is technical. On slow connections, multipart uploads time out silently. Users also try to upload HEIC (iPhone) photos which may not be accepted by the current multer config. You will see "I tried to add photos but nothing happened" reports frequently.

⏰ Moderate

My listing disappeared / expired

30-day listing expiry (Session 3) will confuse users who don't re-read the "Expires in Xd" countdown. Without an expiry notification email, listings just vanish. Sellers will file support: "I posted my car for sale and it's gone." They will also ask how to renew without re-posting from scratch.

📱 Moderate

Layout broken on my phone

The frontend is a single-file vanilla JS app. It works well on modern browsers but Indian users have a very wide device spread: Samsung Galaxy A-series (Chrome), Redmi (MIUI browser), Vivo (Funtouch browser), Nokia (Android Go). Tab bar wrapping, the post-form field overflow, and the modal on small screens (<360px wide) are high-risk areas.

💬 Moderate

"I pressed Interested but the seller never replied"

The current "I'm Interested" flow sends a pre-filled message via POST /api/messages with no notification to the seller. The seller has no push notification, no SMS, no email alert — they only see the inbox badge when they next open the app. In a marketplace context, this is a conversion killer. Expect many complaints about "no response from seller."

🏷️ Moderate

Wrong category / can't find where to post X

The three categories (Real Estate, Vehicles, Household Items) have clear gaps: no Electronics, no Jobs, no Services, no Pets. Indian users will try to post smartphones, TVs, and domestic services. They will either post in the wrong category or give up and report "I can't find the right category for my item."

🌐 Occasional

Requests for Hindi / regional language

At public scale in Bangalore and India broadly, users will request Kannada, Hindi, and Tamil UI. This is a significant feature request but a development scope expansion (i18n system). For MVP, the response is: "English only for now — coming soon." Worth tracking as it signals regional expansion readiness.

🚨 Occasional

Fake listing / scam reports

Public marketplaces attract fraudsters within weeks of launch. Common patterns: listings at unrealistically low prices (bait), seller asking for advance payment via UPI, listings copy-pasted from OLX/Quikr with stock photos. Without a "Report Listing" button, these will come in via the general feedback form or direct WhatsApp to Nagesh/Arun.

🔒 Rare but High Impact

Account security / "someone used my number"

With email verification not yet enforced pre-launch, a user could register with another person's email. At scale, someone will complain "I got an OTP I didn't request" or "an account was created with my email." This is the known pre-launch gap documented in CONTEXT.md — urgent to fix before public release.

⚡ Rare but Important

Feature requests that reveal product gaps

WhatsApp chat button on listing, direct call button (without showing full phone number), price negotiation flow, saved searches with email alerts, "share to WhatsApp" one-tap action. These will come from power users and are actually valuable product signals — worth logging systematically in a Notion or spreadsheet, not just the feedback form.

💡
Feedback collection tip: The current feedback form (POST /api/feedback) stores free-text responses. For public launch, add a structured rating (1–5 stars) and a category dropdown (Bug / Suggestion / Content Report / Other) to the feedback form. This makes triage 5× faster than reading free text.

Good news: Most of the heavy infrastructure is managed for you. Vercel handles deployments, SSL, and function scaling. Supabase handles DB connections, Auth, and Storage. Your daily admin is almost entirely content moderation and communication — not infrastructure firefighting. At MVP scale (<500 MAU), total daily ops time should be under 30 minutes.

Back-End Tasks — If You Were to Hire

A complete list of all back-end responsibilities, showing what a hired developer would own.

Core Ongoing

API development and maintenance

Adding new Express routes as features are built (real-time chat, notifications, saved search alerts, admin dashboard API). Maintaining existing routes in src/routes/ — auth, listings, messages, pins, uploads, users. Keeping route contracts stable so the frontend doesn't break on changes.

Core Ongoing

Database migrations and schema management

Writing numbered SQL migration files in database/migrations/, running them safely in Supabase SQL Editor, verifying with EXPLAIN ANALYZE that new queries use indexes. Adding new tables for features like real-time chat (003-chat-schema.sql is pre-written but not yet applied), saved searches, notifications, review/rating system.

Core Ongoing

Row Level Security (RLS) policy management

Every new table in Supabase needs correctly scoped RLS policies. Getting these wrong can either lock users out of their own data or expose all data publicly. Writing, testing, and auditing policies for each table as the schema grows. This is the most Supabase-specific skill that requires care.

Infrastructure

Performance monitoring and query optimisation

Running EXPLAIN ANALYZE on slow queries flagged by Supabase's slow query log. Adding or tuning GiST indexes on PostGIS columns as the listings table grows. Monitoring Vercel function cold-start times and edge function memory usage. Identifying and fixing N+1 query patterns in the listings + profiles joins.

Infrastructure

Listing lifecycle management

Building the listing expiry cron (send reminder email 3 days before expiry via Resend, update status='expired' at expires_at). Building the listing renewal API (PUT /api/listings/:id/renew resets expires_at = now + 30 days). Handling the cascading deletes correctly when a listing is removed (photos, messages, saved pins).

Infrastructure

Security patching and dependency updates

Monthly npm audit, updating vulnerable packages, testing that the update does not break existing routes. Monitoring Supabase's security advisories. Rotating service role keys if they are ever exposed. Ensuring SUPABASE_SERVICE_ROLE_KEY is never in any client-visible code path — periodic code audit for this.

Feature Work

Notification system (email + optional SMS)

Sellers currently get no notification when a buyer presses "I'm Interested." Building a Resend email trigger on POST /api/messages (seller gets "You have a new inquiry for [listing title]") solves the biggest conversion gap. Later: push notifications via a Web Push API or Firebase Cloud Messaging for browser-based alerts without a native app.

Feature Work

Admin dashboard API

The current admin panel is two menu items hardcoded to nagesh.aadi@gmail.com and arun.bn1@gmail.com. As volume grows, a proper admin API is needed: listing approval/rejection endpoints with reason codes, user suspension endpoint, bulk action support, aggregate stats (total listings, new users today, messages sent today).

Feature Work

Search and ranking improvements

Current search is client-side substring match on listing titles. Backend full-text search using Postgres tsvector / tsquery would cover partial matches, synonyms, and multi-word phrases. Adding a relevance score (proximity × recency × views) to the listing query so popular nearby listings surface first.

Feature Work

Storage management and cleanup

Scheduled job to delete orphaned photos from Supabase Storage (photos whose listing row no longer exists). Enforcing per-user storage quotas to prevent a single bad actor filling Storage. Potentially adding server-side image resizing to reduce CDN egress costs (Supabase Transformation API, available on Pro).

Growth Phase

Analytics and event tracking backend

Tracking what users search, which listing categories are most viewed, drop-off point in the post-listing funnel, messaging conversion rate per listing. This requires an events table or integration with a lightweight analytics backend (PostHog free tier is a natural fit with Supabase). Data becomes valuable for Arun's investor conversations.

Growth Phase

Payment gateway integration (Razorpay)

Currently out of scope (per CLAUDE.md MVP boundary), but when paid boost tiers or featured listings are added, Razorpay integration is the Indian standard. This is a significant back-end milestone — webhook handling, idempotency, refund flows, and invoice generation all need to be correct from day one.

Who to Hire

The right profile for someone who can own the back-end of MapIt, mapped to the actual stack.

👨‍💻

Option A — Full-Stack Developer (Node.js + Supabase)

Best all-round fit for the current MapIt stack. Can own both API and DB work independently.

Must-Have Skills

Node.js / Express PostgreSQL — queries, indexes, migrations REST API design JWT / Auth middleware Git / GitHub workflow Vercel or similar serverless deployment

Nice to Have

Supabase (learnable in 1–2 weeks) PostGIS or spatial SQL Leaflet.js or map APIs Vanilla JS frontend (can read + patch the single HTML file) Resend / SendGrid email API Razorpay (for future payments)

Where to find: LinkedIn (Bangalore), Internshala for freshers, Turing.com for remote, or a referral from the Supabase Discord community. The Supabase Discord has a #jobs channel with active Indian developers who already know the stack.

Approximate cost (Bangalore, 2–3 years exp): ₹8–15 LPA full-time, or ₹800–1,500/day contract. A junior (0–1 yr, with Node.js internship) is ₹4–6 LPA and works well if Nagesh can review PRs.

🛠️

Option B — Back-End Developer Only (Node.js + PostgreSQL)

Focused hire if you want someone who is purely API + DB. Does not touch the HTML frontend.

Must-Have Skills

Node.js PostgreSQL — advanced queries, RLS, schema design API security (rate limiting, input validation, SQL injection prevention) Serverless function model (stateless, cold starts)

Limitation: Any frontend bug (CSS, JS logic in MapIt_MVP_v1.html) still falls on Nagesh or Claude. Suitable only if Nagesh is comfortable maintaining the frontend himself or delegating to Claude Code.

🎓

Option C — Junior Developer + Claude Code as Co-Pilot

Lowest cost. A junior developer handles moderation, testing, SQL, and small fixes — Claude does the heavy implementation.

Must-Have Skills

Basic JavaScript / Node.js Comfortable with Supabase SQL Editor Can run git, npm, and deploy to Vercel Willing to work with AI-assisted code review

Structure: Nagesh reviews code quality and approves PRs; Claude Code writes implementations; the junior developer executes, tests, and handles daily ops. This is the most cost-effective structure for an early-stage marketplace in India.

Approximate cost: ₹3–5 LPA (fresher with Node.js basics). Internships from IITs/NITs are a great source.

💡
Hiring tip specific to MapIt: Ask candidates to open mapit.co.in, post a listing, and describe what they observe in the backend architecture from the network requests alone. Someone who notices the Supabase storage URLs, the /api/listings endpoint returning GeoJSON-style data, and the Vercel serverless signatures is already 80% of the way there.

An honest assessment of what Claude Code can cover, what it cannot, and where the human load falls.

🤖
What "Claude Code as AI Agent" actually means here: Claude Code (this tool) can read every file in the project, write code, run shell commands, run the server, read SQL schemas, and commit to git. It does not run autonomously without Nagesh present. Think of it as a senior developer who is always available for a session but needs Nagesh to initiate each one, review the output, and run the Supabase SQL Editor manually where code cannot reach.

✅ Verdict: Yes — AI + Nagesh alone can manage, up to ~500 Monthly Active Users

For the launch phase (first 3–6 months, family + early-adopter scale), the combination of Claude Code + Nagesh's daily 30-minute ops check is sufficient. Supabase and Vercel eliminate almost all infrastructure management. Claude handles all code — features, bug fixes, RLS policies, migrations. Nagesh provides the human layer that Claude cannot: Supabase SQL Editor, listing moderation, user support, and dashboard monitoring.

Daily time commitment from Nagesh: approximately 30–45 minutes for ops (moderation, logs, feedback). Feature development (new sessions) is additional but planned in blocks, not daily.

⚠️ When to hire: the clear trigger points

Hire when any two of the following are true simultaneously: (1) daily listing moderation takes more than 1 hour; (2) user support messages exceed 20/day; (3) there are 2+ unresolved production bugs open at the same time; (4) Nagesh cannot attend to the app for more than 3 days and Arun cannot cover; (5) a paid feature (Razorpay) is being built. At that point, Option C (junior developer ₹3–5 LPA + Claude as co-pilot) is the most cost-efficient first hire.

⚠️
The one genuine gap: Neither Claude Code nor Nagesh alone constitutes a monitoring system. If the Vercel function throws 500 errors at 2am while you are asleep, nobody knows until morning. Setting up a free Sentry alert or Vercel email notification for error rate spikes costs nothing and closes this gap completely without a hire.
