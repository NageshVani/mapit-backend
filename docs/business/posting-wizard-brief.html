Posting Wizard — Design Brief

For Arun · prepared by James for Nagesh · 8 Nov 2026 · Design only, no code yet
Status: waiting for your answers (section 6). Build starts after the review queue (9L) is live on mapit.co.in.
In one paragraph: today a seller fills one long form to post a listing. On a phone that feels like a lot, and some people give up halfway. The wizard splits the same form into 5 short screens, one topic each, with a Next button. Nothing new is asked of the seller; the questions are the same, just in smaller pieces. This was your idea (12 Oct), and Nagesh fixed the screen order on 20 Oct.

1. What is already in place

  • live The form already has numbered sections and a step bar at the top (20 Oct).
  • live Auto-title: the title fills itself from the details (e.g. "Maruti Swift 2014 – 52,000 km, 1st owner"), and stops once the seller types their own.
  • live "✨ Write it for me" drafts the description.
  • on UAT Review queue (9L): every new listing waits for an approver; the seller can be asked to change something and then resubmits.

So the wizard is mostly about turning the existing sections into screens, not building a new form.

2. The 5 screens

1What
Real Estate / Vehicles / Household → type → Sell or Rent
Next: type chosen
2Details
Questions for that type, title (auto), description (✨)
Next: title filled
3Price & photos
Price (shown in words), up to 5 photos
Next: price + 1 photo
4Location
Pin on map, search or GPS, "Show exact pin"
Next: pin placed
5Review & contact
Phone choice + summary card
Submit for review

On a phone, swipe sideways to see all five.

#ScreenWhat the seller does"Next" becomes active when
1WhatPicks category, type (e.g. 2BHK flat, car, sofa) and Sell or RentA type is chosen
2DetailsAnswers the questions for that type; checks the auto-title; writes or generates the descriptionThe title is filled
3Price & photosEnters the price (shown in words, e.g. "₹ 4.5 lakh"); adds up to 5 photosPrice above 0 and at least 1 photo (plots excepted, see question 2)
4LocationPlaces the pin (search, GPS or tap); chooses whether buyers see the exact pin or the approximate areaThe pin is placed
5Review & contactChooses how buyers can contact them; checks a summary (photo, title, price, area)→ Submit for review

Why this order

  • Category first because it decides which questions appear on screen 2.
  • Map late because it is the heaviest screen to load. By screen 4 the seller has already put in effort and is less likely to quit.
  • Privacy choice right before submit ("Show exact pin", phone sharing), where the seller is most likely to read it.

3. How it behaves

  • Back never loses anything. Everything typed stays when moving between screens.
  • The phone's back button goes to the previous screen, not out of the form. (This is the most common annoyance in phone forms.)
  • Accidental refresh or close: the seller can continue from a saved draft (details in question 1).
  • Step bar on every screen. When editing an existing listing, every step can be tapped, so a seller who only wants to fix the price jumps straight to screen 3.
  • "Needs change" link (new): when an approver asks for a change, "Edit & resubmit" opens the wizard on the screen that needs fixing. Example: reason "Price missing or unrealistic" opens screen 3.
  • After Submit: a clear "Sent for review — usually within 4 hours" screen, matching the review queue.

4. A bigger question: one file or several

The whole website (map, listings, posting, chat, sign-in) is one file of about 5,900 lines. That was the right choice for building the MVP quickly. It is now causing real friction:

  • Everything changes the same file, so two features can't be worked on at the same time. Today, for example, the wizard has to wait because the review queue changed the same file.
  • Any small fix makes every visitor download the whole app again (about 345 KB).
  • Easier to break something by accident, because all parts share one space.

Proposal: split it into a few plain files (one for the look, about 6–8 for the parts: map, listings, posting, chat…). Visitors see no difference; no new tools and no cost. It is about one working session, done at a quiet moment, right after the review queue goes live and before the wizard. The wizard then gets its own file from day one instead of being moved later.

James's recommendation: split first, then the wizard. A full rebuild with a modern framework is not needed now; that is a "version 2" topic.

5. Proposed order after the review queue is live

  1. Small: show "👁 views" on each seller's My Listings, and don't count the seller's own visits (view counts stay public, decided 8 Nov).
  2. Split the one big file into several (section 4), about 1 session.
  3. Posting wizard, about 1 session; phone mockups for your approval first.

No database changes and no new monthly costs for any of the three.

7. Technical notes (for Nagesh and James)

  • Keep the existing field IDs (e.g. pf_total_price) so save, edit, auto-title and "Write it for me" keep working unchanged.
  • Leaflet blank-map trap: a map inside a hidden screen draws grey tiles. Call invalidateSize() when screen 4 opens.
  • Phone back button: push a history entry per screen and listen for popstate.
  • "Next" checks are for convenience only; the server keeps validating every field (Rule 8).
  • File split: keep functions global (buttons use onclick), load scripts in a fixed order, and add a version tag (app.js?v=…) so phones don't keep an old copy. The split may also end the "two copies of the page" rule.
